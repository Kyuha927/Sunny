## 1. 클로드 코드 토큰 소진의 구조적 원인 이해
<mark>클로드 코드 사용 시 토큰이 불필요하게 소모되는 구조적 원인을 이해하고 관리하는 것이 중요하다.</mark>

### 1.1. AI 대화 방식과 토큰 소모의 기본 원리
1. **AI는 대화 시 이전 내용을 모두 재검토한다.**
   1. 카카오톡과 달리, AI는 메시지를 보낼 때마다 대화방의 모든 내용을 처음부터 끝까지 다시 읽는다.
   2. 이 과정에서 읽는 모든 내용이 **토큰**으로 소모된다.
2. **대화가 길어질수록 비용이 증가한다.**
   1. 대화가 길어지거나 파일을 많이 읽을수록, 같은 질문 하나에도 비용이 올라가는 구조이다.
   2. 예를 들어, 열 번째 프롬프트를 요청하면 AI는 이전 아홉 개의 요청과 응답 전부를 다시 읽는다.
3. **비용은 대화방에 담긴 내용에 의해 결정된다.**
   1. 이 대화방의 내용을 효율적으로 관리하는 기술을 **컨텍스트 엔지니어링**이라고 한다.
2. **컨텍스트 관리가 미흡하면 AI 품질도 저하된다.**
   1. 대화방에 메시지가 많아지면 비용 문제 외에도 **AI 품질 자체가 떨어진다(아보 현상)**.

### 1.2. 핵심 전문 용어 정의
1. **토큰(Token)**
   1. AI가 텍스트를 처리하는 **최소 단위**이다.
   2. 글자, 단어, 코드 한 줄 등이 토큰 단위로 쪼개져 처리된다.
2. **컨텍스트 윈도우(Context Window)**
   1. AI가 **한 번에 처리할 수 있는 토큰의 총량**이며, 작업 공간의 크기와 같다.
   2. 프롬프트 입력, 파일 첨부 등 모든 요청 내용이 토큰으로 변환되어 이 윈도우 안에 채워진다.
   3. 클로드 모델(Opus, Sonnet, Haiku)은 기본적으로 20만 토큰을 지원하며, Sonnet과 Opus는 베타로 100만 토큰을 지원한다.
3. **컨텍스트 엔지니어링(Context Engineering)**
   1. 이 작업 공간(컨텍스트 윈도우)을 **효율적으로 관리하는 기술**이다.
   2. 필요한 것만 넣고 불필요한 것은 빼며 상황에 따라 컨텍스트를 정리하는 행위이다.

### 1.3. 컨텍스트 관리 실패 시 발생하는 악순환
1. **컨텍스트 로스(Context Loss) 발생**
   1. 작업 A를 끝내고 컨텍스트를 비우지 않은 채 작업 B를 시작하면, A에서 읽었던 파일, 에러 로그 등이 계속 남아 토큰을 소모한다.
2. **AI 환각(Hallucination) 유발**
   1. 관련 없는 정보가 많거나 컨텍스트 윈도우가 가득 차면 AI가 헷갈려 **틀린 답(환각)**을 말하기 시작한다.
   2. 개발 시 환각으로 인해 오류 수정에 시간을 쓰고 토큰을 재소비하게 된다.
3. **악순환의 반복**
   1. 컨텍스트 관리를 안 하면 토큰 낭비, 환각 유발, 퀄리티 저하로 인한 재작업으로 토큰 재소진이라는 악순환이 반복된다.

## 2. 구독 플랜 및 모델 선택에 따른 전략
<mark>사용자의 구독 플랜과 선택한 모델에 따라 토큰 소모량이 크게 달라지므로, 이에 맞는 전략을 수립해야 한다.</mark>

### 2.1. 구독 플랜별 사용 가능 시간 비교
1. **플랜별 사용 가능 시간 확인이 중요하다.**
   1. 같은 Opus 모델을 사용해도 Pro 플랜과 Max 플랜은 사용 가능한 양이 완전히 다르다.
2. **세 가지 구독 플랜의 사용량 (공식 수치)**
   1. **Pro 플랜**: Sonnet 주당 40~80시간, **Opus 모델 매우 제한적 사용 가능**.
   2. **Max $100 플랜**: Sonnet 주당 140~280시간, Opus 주당 15~35시간 사용 가능.
   3. **Max $200 플랜**: Sonnet 주당 240~480시간, Opus 주당 20~40시간 사용 가능.
3. **Pro 플랜 사용 시 주의점**
   1. Pro 플랜은 Opus 모델 사용이 매우 제한적이며, 전체 사용량 자체가 적어 Opus를 계속 사용하면 2일 만에 주간 사용량의 80%가 소진될 수 있다.
   2. **결론적으로 플랜에 따라 Opus 사용 전략을 완전히 다르게 가져가야 한다.**

### 2.2. 플랜별 권장 Opus 사용 전략
1. **Pro 플랜 사용자**
   1. **Sonnet 위주**로 사용하고, Opus 모델은 정말 필요할 때만 사용해야 한다.
   2. Opus가 똑똑해도 항상 사용하면 토큰이 금방 소진되므로, 대부분의 코딩 작업은 Sonnet으로 충분하다.
2. **Max $100 플랜 사용자**
   1. Opus 모델을 적당히 활용하면서 모니터링을 병행해야 한다.
3. **Max $200 플랜 사용자**
   1. Opus 모델을 비교적 자유롭게 활용할 수 있다.

### 2.3. 모델별 성능 및 비용 차이
1. **모델별 특징 비교**
   1. **Opus**: 가장 똑똑하며 토큰이 **4~5배 더 소모**되며, 복잡한 설계나 어려운 문제 해결에 유용하다. (시니어 개발자 비유)
   2. **Sonnet**: 균형 잡힌 모델로 일반 코딩, 파일 수정, 기능 구현 등 **대부분의 작업에 충분**하다. (중급 개발자 비유)
   3. **Haiku**: 가장 빠르고 저렴하며 간단한 질문이나 파일 검색에 효과적이다. (주니어 개발자 비유)
2. **낭비 방지**
   1. 시니어 개발자(Opus)에게 복사 붙여넣기(단순 작업)를 시키는 것은 낭비이다.

## 3. 모델 설정 및 컨텍스트 관리 기술 (6가지 팁)
<mark>설정 변경, 명령어 사용, 프롬프트 습관 개선을 통해 토큰 낭비를 막고 컨텍스트를 효율적으로 관리하는 실용적인 팁을 적용해야 한다.</mark>

### 3.1. 기본 모델 설정 및 자동 전환 기능 활용
1. **현재 모델 확인 및 기본 모델 고정**
   1. `/model` 명령어로 현재 설정된 모델을 확인할 수 있다.
   2. **Pro 플랜 사용자는 Opus로 설정되어 있다면 즉시 Sonnet으로 변경해야 한다.**
   3. 설정 파일(`settings.json`)에 모델을 Sonnet으로 설정해 두면, 클로드 코드를 켤 때마다 항상 Sonnet으로 시작하게 된다.
   4. 세션 중간에 모델을 변경하려면 `/model opus` 또는 `/model sonnet` 명령어를 사용한다.
2. **Opus Plan을 이용한 자동 모델 전환**
   1. **Opus Plan**은 상황에 따라 모델을 자동으로 전환해 주는 기능이다.
   2. 계획 모드에서는 Opus를 사용하고, 계획 승인 후 실행 모드로 넘어가면 자동으로 Sonnet으로 전환된다.
   3. 설정은 `/model opusplan` 명령어나 설정 파일에서 할 수 있다.
3. **공식 문서 확인 습관**
   1. AI 도구 사용 시 공식 문서에서 스펙을 확인하는 습관이 중요하다.

### 3.2. 컨텍스트 초기화 및 압축 명령어 활용
1. **작업 완료 후 컨텍스트 초기화**
   1. AI에게 프롬프트를 요청하면 이전 프롬프트를 전부 읽으므로, 하나의 작업이 완료되면 `/clear` 명령어로 메시지를 초기화해야 한다.
2. **세션 이름 지정 및 재개**
   1. `/clear` 전에 `rename` 명령어로 세션 이름을 지정해 두면, 나중에 `/resume` 명령어로 해당 대화로 쉽게 돌아갈 수 있다.
3. **컨텍스트 윈도우가 가득 찼을 때 압축**
   1. `/compact` 명령어를 수행하여 대화 내용을 요약하면, 클로드가 중요도를 판단하여 내용을 압축한다.
   2. 이때 중요한 내용은 요약 내용에 반드시 포함해야 한다.

### 3.3. 확장된 사고(Extended Thinking) 기능 제어
1. **확장된 사고 기능의 토큰 소모**
   1. 이 기능은 클로드가 답변 전에 깊이 생각하는 기능으로 기본 활성화되어 있으며 **최대 3만 토큰 이상**을 사용한다.
   2. **Thinking 토큰이 출력 토큰으로 과금**되므로, 단순한 파일 수정에도 많은 토큰이 소모될 수 있다.
2. **기능 제어 방법**
   1. `/config` 명령어를 통해 **Thinking 모델을 끌 수 있다.**
   2. 환경 변수를 통해 예산을 낮출 수도 있다.

### 3.4. 구체적인 프롬프트 작성 습관
1. **구체적인 요청이 토큰을 절약한다.**
   1. "이 코드를 개선해 줘"라고 요청하면 클로드가 프로젝트 전체를 탐색하며 토큰이 많이 소모된다.
   2. 반면, "해당 파일에 있는 로그인 함수에 입력값을 검증해 줘"와 같이 구체적으로 요청하면 해당 파일 하나만 열고 작업하여 토큰 차이가 수십 배 날 수 있다.

### 3.5. MCP Tool Search 비활성화 (다중 서버 연결 시)
1. **MCP Tool Search의 기본 동작**
   1. MCP 서버 여러 개를 연결하여 사용할 경우, 기본값인 `auto` 설정은 컨텍스트 윈도우의 10%를 초과할 때 발동된다.
2. **항상 비활성화 권장**
   1. 화자는 이 옵션을 항상 켜두기 위해 `off`로 설정하여 해당 옵션을 비활성화한다.

### 3.6. 메모리 파일(.md) 관리 전략
1. **CLAUDE.md 파일 용량 제한**
   1. 공식 문서는 **CLAUDE.md 파일을 약 500줄 이하로 유지**할 것을 권장한다.
2. **상세 지식은 스킬(Skill)로 분리**
   1. 상세 지식은 스킬로 분리해야 하는데, 스킬은 필요할 때만 로드되기 때문이다.
   2. CLAUDE.md에는 항상 해줘야 하는 핵심 규칙만 남기고, 가끔 쓰는 상세 지식은 스킬로 빼면 매 세션 기본 토큰 소모가 효과적으로 줄어든다.

## 4. 최종 점검 및 구독 플랜별 관리 강조
<mark>컨텍스트 관리는 정답이 없으며 구독 플랜에 따라 엄격한 전략을 적용해야 하며, 결과가 없다면 다른 도구를 고려하는 것도 방법이다.</mark>

### 4.1. 컨텍스트 관리의 다양성과 구독 플랜의 중요성
1. **다양한 관리 방법 존재**
   1. 컨텍스트 관리에는 정해진 정답이 없으며 방법이 다양하다.
   2. 서브에이전트에게 무거운 작업을 위임하거나, 훅(Hook)을 통해 테스트 로그를 전 처리하여 에러만 클로드에게 넘기는 방법 등이 있다.
2. **구독 플랜에 따른 엄격한 전략 요구**
   1. 컨텍스트 관리 전략은 **구독 플랜에 따라 달라져야 한다.**
   2. **Pro 플랜 사용자**는 엄격한 관리 전략을 사용하고 기본 모델을 Sonnet으로 고정해야 하며, Opus 모델 사용을 최소화해야 한다.
3. **결과에 따른 다음 단계**
   1. Pro 플랜에서 컨텍스트 관리를 충실히 했음에도 결과가 잘 나온다면 구독 플랜을 천천히 올릴 수 있다.
