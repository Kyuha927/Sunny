# 나만의 AI 코딩 에이전트 만들기: Pi의 작동 원리

## 1. 게스트 소개 및 마리오의 배경
<mark>오스트리아 출신 소프트웨어 개발자인 마리오 체흐너가 직접 만든 코딩 에이전트 'Pi'의 개발 배경과 그의 다채로운 커리어를 소개한다.</mark>
### 1.1. 게스트 소개
1. **마리오 체흐너(Mario Zechner)**는 **나만의 코딩 에이전트**를 직접 만들어 증명한 오스트리아 출신 소프트웨어 개발자이다.
2. 그가 만든 코딩 에이전트 **'Pi'**는 Claude Code와 경쟁할 수 있을 정도로 성능이 뛰어나며, 인터뷰어 본인도 현재 개발 중인 플랫폼에 활용하고 있다.

### 1.2. 마리오의 다채로운 커리어
1. 마리오는 **반학술 분야**에서 **자연어 처리(NLP)**와 **정보 검색** 분야로 커리어를 시작했다.
   1. 이는 LLM이나 트랜스포머 등장 훨씬 이전이었으나, 머신러닝의 기본적인 이해를 갖추는 데 기여했다.
2. 이후 샌프란시스코에서 1년간 **게임 개발**을 했으며, 스타트업의 테크 리드로 일했다.
3. 오스트리아 복귀 후 반학술 분야에서 관리직을 맡았고, 이후 스웨덴 친구들과 **컴파일러 엔지니어링** 관련 스타트업을 성공적으로 매각했다.
4. 현재는 시애틀의 친구와 함께 **2D 애니메이션 소프트웨어 'Spine'**을 개발하고 있으며, 이 분야에서 선두주자이다.
   1. Spine은 **2D 스켈레탈 애니메이션** 분야의 니치 제품으로, 게임 업계의 큰 이름들이 라이선스를 사용하고 있다.
   2. 스켈레탈 애니메이션은 **스켈레톤(뼈대)**을 만들고 이미지에 붙여 움직이는 방식으로, 런타임에 동적으로 반응할 수 있어 스프라이트 시트 방식보다 효율적이다.
   3. 이는 클래식한 레트로 느낌의 스프라이트 애니메이션과 달리, **Dead Cells**나 **Prince of Persia** 스타일의 생동감 있는 애니메이션에 더 적합하다.

## 2. AI 분야로의 복귀와 LLM 활용 시작
<mark>마리오는 우크라이나 전쟁으로 인한 물가 폭등 시기, 데이터 스크래핑을 계기로 LLM을 활용하기 시작했으며, 구조화된 데이터 추출의 중요성을 깨달았다.</mark>
### 2.1. LLM 활용 계기: 가격 스크래핑과 데이터 추출
1. 마리오는 2023년 우크라이나 전쟁으로 인한 **물가 폭등**에 대응하기 위해 데이터 스크래핑을 시작했다.
2. 초기 LLM을 활용하여 제품명으로 코카콜라 여부를 판단하는 등 **작은 NLP 작업**을 수행하며 오스트리아 식료품 가격을 스크래핑했다.
3. 이 과정에서 모든 업체의 최저가가 정확히 같은 시점에 인상되는 것을 발견했다.
4. 이후 기자들의 조사 작업을 돕기 위해 **팟캐스트/TV 쇼 설명문**에서 진행자와 게스트의 이름 및 직함을 **구조화된 형태로 추출**하는 데 LLM(GPT-3.5)을 성공적으로 사용했다.

### 2.2. 구조화된 데이터의 중요성 및 결정론적 코드
1. 데이터를 **미리 정의된 구조**로 만들고 모델을 사용해 채우면, **비교 가능성**과 **자동 검증** 수준이 높아진다.
2. 신뢰할 수 있는 제품을 만들려면, AI를 통한 추론 단계를 최소화하고 나머지 부분은 **결정론적인 고전 코드**로 구현해야 한다는 것이 반복되는 교훈이다.

## 3. 툴 콜링과 코딩 에이전트의 등장
<mark>LLM이 툴 콜링 기능을 갖추게 되면서 코딩 분야에 흥미로운 활용이 열렸고, Claude Code의 등장은 에이전트의 활용 범위를 파일 단위에서 코드베이스 전체로 확장시켰다.</mark>
### 3.1. 툴 콜링과 에이전트 실험
1. LLM이 **툴 콜링(Tool Calling)**이 가능해지면서 코딩이나 컴퓨터 사용 같은 흥미로운 활용 분야가 열렸다.
   1. 툴 콜링은 LLM에게 함수 이름과 매개변수를 알려주면, 해당 정보가 포함된 텍스트를 출력하는 단순한 텍스트 입출력 방식이다.
2. 마리오는 이 기능을 활용해 소프트웨어 개발 과정에 통합하는 실험을 진행하고 그 결과를 공유했다.

### 3.2. Claude Code의 혁신과 WipeTunnel 개발
1. 2024년 4월, **Claude Code** 출시(인기 폭발)는 터미널 UI를 제공하며 코딩 에이전트 이슈를 확산시켰다.
2. 이전 도구(Cursor)는 파일 내 제안이나 제한된 파일과의 채팅 수준이었으나, Claude Code는 **파일시스템 탐색 및 코드 조각 검색** 기능, 즉 **에이전틱 서치(Agentic Search)**를 제공했다.
3. 이로 인해 에이전트가 **전체 코드베이스를 탐색하고 수정**할 수 있게 되어 활용 사례가 완전히 바뀌었다.
4. 마리오와 동료들은 Claude Code CLI를 모바일에서도 사용하고 여러 인스턴스를 동시에 관리하기 위해 24시간 만에 **WipeTunnel**을 개발했다.
   1. WipeTunnel은 웹 인터페이스를 제공하는 Claude Code 서버 역할을 했다.
5. WipeTunnel 개발 시, **수동 코딩 없이 에이전트에게만 코드를 쓰게 하고 리뷰만 하는 방식**으로 작업했으나, 이는 에이전트에게 모든 것을 맡기는 **바이브코딩**과는 다르다고 선을 그었다.

### 3.3. 이동 중 사용의 어려움과 개인용 어시스턴트 접근법
1. 인터뷰어 역시 Claude Code로 시작해 **OpenCode**로 옮겨 **OpenCode to Go**라는 병렬 세션 앱을 만들었으나 만족스럽지 못했다.
2. 기술적으로 가능해지면 **이동 중에도 쓰고 싶어지지만**, 하루 종일 에이전트에게 명령만 내리기보다 삶을 즐기고 싶다는 현실적 제약이 있다.
3. 특히 터미널 UI를 모바일에서 스트리밍하는 것은 **폼팩터 문제**로 가독성이 떨어진다.

## 4. 개인용 어시스턴트와 샌드박싱 딜레마
<mark>비기술자에게도 유용한 개인용 어시스턴트 개발이 진행 중이나, 에이전트의 유용성을 위해 필요한 권한(명령 실행, 데이터 접근, 네트워크 접근)이 심각한 보안 위험을 초래한다.</mark>
### 4.1. 개인용 어시스턴트의 목표와 인터페이스
1. 현재 목표는 **개인용 어시스턴트**를 비기술자에게 제공하는 것으로, 이는 코드를 생성/실행하여 엑셀 파일 작성이나 차트 생성 등을 수행한다.
2. 핵심은 전용 UI 대신 **Slack, Discord, Telegram 등 기존 채팅 앱에 통합**하는 것이다.
3. 일반 사용자에게는 활동에 대한 **친화적인 요약**만 보여주고, 뒤에서 일어나는 Bash 실행이나 코드 작성 내역은 숨긴다.
4. 이러한 인터페이스는 이동 중인 사용자에게도 Bash 출력보다 선호되며, 캘린더 항목 작성이나 이메일 답장 우선순위 확인 등에서 잘 작동한다.

### 4.2. 치명적 삼위일체와 프롬프트 인젝션 위험
1. 에이전트가 유용하려면 이메일, CMS, CRM 등 **민감한 데이터에 접근**해야 하는 딜레마가 있다.
2. 문제는 현재 LLM이 **사용자 입력**과 **파일/웹사이트에서 읽은 입력**을 구분하지 못한다는 점이다.
3. 이로 인해 공격자가 웹사이트 내용에 악성 명령(예: SSH 키 추출)을 삽입하여 LLM이 이를 사용자 명령으로 오인하게 만들 수 있다.
4. **Simon Willison**은 **명령어 실행, 데이터 읽기, 네트워크 접근**의 세 가지 권한을 주면 항상 취약해지는 것을 **"치명적 삼위일체(Lethal Trifecta)"**라고 명명했다.
5. 이 세 가지 권한은 이메일 읽기/답장 등 유용한 작업을 위해 필수적이므로 해결이 어렵다.

### 4.3. 보안 문제에 대한 현재의 대응과 딜레마
1. 일부는 **권한 대화 상자(허용/거부)**로 해결하려 하지만, 에이전트가 너무 빨라 사용자가 보모 역할을 하기 싫어한다.
2. Anthropic의 **Cowork**가 개인용 채팅 인터페이스를 제공했으나, 출시 24시간도 안 되어 프롬프트 인젝션이 시연되었다.
3. **프론티어 랩(OpenAI, Anthropic)**은 소비자 시장 진입 및 VC 상환 압박으로 보안 문제를 무시하고 사용자에게 책임을 전가하고 있다.
4. 마리오는 자신의 시스템은 키 로테이션 등으로 안전하게 설계했지만, 일반 사용자는 이해할 수 없는 위험에 노출된다.

## 5. 브라우저 에이전트와 보안 위험의 심화
<mark>브라우저 에이전트 역시 동일한 취약점을 가지며, 브라우저가 운영체제 안의 운영체제 역할을 하므로 피해 가능성이 매우 크다.</mark>
### 5.1. 브라우저 에이전트의 취약성
1. **OpenAI 브라우저**나 마리오가 개발한 브라우저 플러그인 역시 에이전트가 브라우저를 제어하는 방식이므로 동일한 취약점을 가진다.
2. 브라우저는 비밀번호와 로그인 계정이 저장된 **컴퓨터의 중심**이 되었으므로, 여기서 문제가 발생할 경우 피해 가능성이 매우 크다.

### 5.2. 현재 브라우저 에이전트의 낮은 사용률과 유용한 활용처
1. 마리오의 경험상, **Atlas, DIA, ARK** 같은 브라우저 관련 제품들은 사용자가 거의 없다(이탈률이 높다).
2. 솔직히 말해, 현재 이러한 에이전트들은 **기술자**가 어떻게 명령해야 유용한지 알 때만 잘 작동한다.
   1. 마리오 본인은 웹사이트 즉석 스크래핑이나 긴 글 요약에는 유용하다고 본다.
3. 쇼핑이나 여행 예약처럼 **완전히 맡기기 어려운 유즈 케이스**는 일반 사용자에게 적합하지 않다.
4. 에이전트의 잠재력은 **비즈니스 레거시 워크플로우** 자동화에 있다.
   1. SAP 같은 구식 시스템의 고통을 겪는 기업들이 많으며, **휴먼 인 더 루프(Human In The Loop)** 방식으로 자동화할 수 있다.
   2. 엔터프라이즈 환경의 시스템(SaaS, SAP 모듈)은 복잡하고 불친절하여(그린디), 에이전트가 휴가 신청 같은 반복 작업을 대신해주면 유용하다.
5. LLM은 **비구조화된 콘텐츠를 구조화된 콘텐츠로 번역**하는 '라스트 마일'에 강하지만, 그 이후는 여전히 **결정론적 코드로 처리**하는 것이 투명성과 효율성 면에서 낫다.

## 6. 유럽의 AI 현황: 데이터 주권과 실행력 문제
<mark>유럽은 지정학적 문제와 대안 부재로 인해 미국 프론티어 랩에 의존할 수밖에 없으며, 자체 프로젝트의 실행력과 벤처 캐피털 문화 부재가 문제이다.</mark>
### 6.1. 지정학적 위험과 유럽 대안의 부재
1. 유럽은 **디지털 주권** 문제에 직면해 있으며, 현재 유럽의 유일한 프론티어 랩인 **Mistral**의 품질이 아직 부족하다.
2. 유럽 기업들은 결국 미국 기업(OpenAI, Anthropic)에 의존하게 되며, 이는 미국 정부의 결정에 따라 서비스가 차단될 지정학적 위험을 내포한다.
3. 데이터 주권 측면에서도, Azure 계약을 해도 데이터가 미국으로 가서 **NSA의 산업 스파이 분석**에 노출될 위험이 현재 보장되지 않는다.
4. 유럽 대안이 있다면 데이터 주권 논의가 가능하겠지만, 현재는 대안이 없어 문제가 묻혀있다.

## 1. AI 시대의 개발자 자세와 '의도적 수련'
<mark>AI 시대에는 AI를 단순 도구가 아닌 실력 향상의 거울로 보고, 의도적이고 의식적인 수련이 필요하다.</mark>
### 1.1. AI에 대한 회의론의 원인 분석
1. **"AI가 안 통한다"는 말의 의미**
   1. 이 말은 특정 회사 **유산 코드베이스**나 **사내 독점 패턴**에 AI를 적용했을 때의 경험일 수 있다
   2. 이러한 환경에서는 AI가 학습 데이터로 접하지 못한 패턴 때문에 잘 안 될 수 있음을 이해해야 한다
2. **걱정되는 개발자 유형**
   1. 독점 코드베이스 경험만 있는 개발자는 집에서 **의도적이고 의식적인 수련**을 해보지 않았을 수 있다

### 1.2. AI를 악기에 비유한 의도적 수련의 중요성
1. **AI의 '아름다움' 발견**
   1. AI는 일종의 **악기**와 같다
   2. 예를 들어, TB-303이나 기타처럼, 처음에는 어려워도 꾸준한 **시간, 노력, 실험**을 통해 새로운 결과물을 만들 수 있다
2. **성과를 내는 개발자의 특징**
   1. AI를 통해 큰 성과를 내는 사람들은 **의도적·의식적 수련**을 해온 사람들이다
   2. 이들은 AI가 엉뚱한 답을 내놓았을 때 포기하지 않고 계속 시도한다

## 3. '랄프 루프(Ralph Loop)' 기법의 등장과 철학
<mark>랄프 위검(Ralph Wiggum) 기법은 LLM의 실패와 피드백을 반복적으로 주입하여 자율 에이전트를 훈련시키는 혁신적인 방법론이다.</mark>
### 3.1. 랄프 위검(Ralph Wiggum)의 정의와 작동 방식
1. **랄프의 정체**
   1. 랄프는 하나의 **기법(technique)**이며, 가장 순수한 형태는 Bash 루프이다: `while :; do cat PROMPT .md | claude-code ; done`
2. **랄프의 적용 범위와 특징**
   1. 대부분의 회사 **그린필드(신규) 프로젝트**에서 아웃소싱 대부분을 대체할 수 있다
   2. 결함이 있지만, 다양한 스타일의 프롬프트를 통해 식별 및 해결 가능하다
   3. **비결정적인 세계에서 결정론적으로 나쁘다**는 점이 랄프의 아름다움이다
3. **랄프 개발 과정의 교훈**
   1. 랄프가 잘못된 방향으로 갈 때, 도구를 탓하기보다 **자신을 돌아보며 랄프를 조율(tuning)**해야 한다

### 3.2. 랄프의 튜닝 과정: 실패를 통한 학습
1. **놀이터 구축과 실패**
   1. 처음에는 놀이터 없이 시작하여 랄프에게 놀이터를 만들게 한다
   2. 랄프는 놀이터를 잘 만들지만, 미끄럼틀에서 굴러떨어지는 등 결함이 발생한다
2. **표지판을 통한 튜닝**
   1. 실패 시, 미끄럼틀 옆에 **표지판**("뛰어내리지 말고, 주변을 살펴봐")을 세워 랄프의 행동을 유도한다
   2. 이 과정을 통해 랄프는 표지판만 생각하게 되며, **결함투성이였던 랄프가 아닌 새로운 랄프**로 진화한다

### 3.3. '두 명의 랄프' 이야기: 철학적 차이
1. **Ralph Wiggum 기법의 핵심**
   1. 순수한 지능이나 추론보다는 **무식한 힘(brute force), 실패, 반복**에 의존한다
2. **Huntley Ralph (Bash 스크립트)**
   1. 모델의 전체 출력(로그, 스택 트레이스, 환각 포함)을 다음 입력으로 파이핑하여 **"컨텍스트 압력솥"**을 만든다
   2. **순진한 지속성(naive persistence)**을 통해, LLM이 날것의 피드백 속에서 자기 난장판을 직면하도록 강제한다
3. **공식 Ralph (Anthropic 플러그인)**
   1. **"실패는 데이터다(Failures Are Data)"** 원칙을 중심으로 설계되었다
   2. **Stop Hook**을 사용하여 AI의 종료 시도를 가로채고, 완료 약속이 충족되지 않으면 실패를 구조화된 데이터로 주입한다
   3. **Huntley Ralph**는 혼돈스럽고 창의적인 탐색에 적합하며, **공식 Ralph**는 안전 훅에 묶여 신뢰성 있는 수정을 위해 설계되었다

### 3.4. 랄프가 제공하는 가치와 성과
1. **주요 활용 영역**
   1. **새 프로젝트** 및 **자동 검증(테스트, 린터)**이 가능한 작업에서 빛을 발한다
2. **효율성 증명 사례**
   1. 5만 달러 계약을 API 비용 297달러로 완료하는 **차익거래** 사례가 보고되었다
   2. Y Combinator 해커톤에서 **하룻밤 사이에 6개 레포지토리를 출시**했다
   3. 인간 입력 없이 14시간 자율 세션으로 **React v16에서 v19로 코드베이스를 업그레이드**한 사례가 있다
3. **핵심 혁신: Stop Hook의 작동 원리**
   1. 플러그인은 Claude 세션 내부에 **Stop Hook**을 설치하여 종료를 차단한다
   2. 훅이 약속을 발견하지 못하면 종료를 차단하고 같은 프롬프트를 다시 주입하여 **자기참조적 피드백 루프**에 가둔다
   3. 이는 AI에게 **진짜 애자일(Agile)**을 적용하여, 티켓 하나를 끝내고 다음 티켓을 찾도록 만든다

### 3.5. 커뮤니티 반응과 잠재적 위험
1. **커뮤니티 반응**
   1. 일부 개발자들은 랄프를 **"AGI에 가장 가까운 것"**이라고 평가했다
2. **비용 및 보안 위험**
   1. 멈추지 않는 API 호출로 인해 **토큰 예산이 소진**될 수 있다
   2. **`--max-iterations` 플래그**를 설정하여 무한 루프를 방지해야 한다
   3. 보안을 위해 AI에게 터미널 제어권을 주는 **`--dangerously-skip-permissions` 플래그** 사용 시, **샌드박스 환경**에서 실행해야 한다

## 4. 랄프 루프를 통한 근본적인 개발 패러다임 변화
<mark>소프트웨어 개발은 벽돌 쌓기 방식에서 벗어나, 루프 자체를 프로그래밍하는 '랄프 마인드셋'으로 전환되고 있다.</mark>
### 4.1. 개발 방식의 근본적 변화
1. **가속이 아닌 접근 방식의 변화**
   1. AI 사용은 단순히 속도를 올리는 가속이 아니라, **접근 방식, 기법, 모범 사례**의 근본적인 변화이다
2. **젠가 방식에서 루프 접근 방식으로**
   1. 표준 개발 방식은 수직으로 벽돌을 쌓는 **젠가(Jenga)** 방식이었다
   2. 이제는 모든 것을 **"루프(loop)"**로 접근하며, 랄프는 자율 개발을 위한 **마인드셋**이 되었다
3. **엔지니어의 역할 변화**
   1. 엔지니어는 벽돌을 쌓는 대신, **루프 자체를 프로그래밍**하여 직무 기능을 자동화한다

### 4.2. 랄프 마인드셋의 핵심: 모놀리식 자율성
1. **멀티 에이전트 복잡성 회피**
   1. 현 단계에서 멀티 에이전트, 에이전트-투-에이전트 통신은 불필요한 복잡성을 야기한다
   2. 비결정적인 마이크로서비스는 **시뻘겋게 달아오른 난장판**이 될 수 있다
2. **랄프의 모놀리식 구조**
   1. 랄프는 **모놀리식**이며, 단일 프로세스, 단일 레포지토리에서 자율적으로 동작한다
3. **도자기 물레 비유와 학습**
   1. 소프트웨어는 **도자기 물레 위의 점토**와 같아서, 마음에 들지 않으면 다시 던져 올려 수정하면 된다
   2. 랄프는 **오케스트레이터 패턴**이며, 루프를 지켜보는 과정에서 개인의 성장과 학습이 발생한다
   3. 실패 영역을 보며 엔지니어 관점으로 문제를 해결해야 한다
4. **실무적 적용**
   1. 프롬프팅으로 루프를 수동으로 돌리거나, 자동화하되 **CTRL+C로 멈춤을 제어**하는 것도 "랄프ing"이다
   2. 랄프의 핵심은 **컨텍스트 엔지니어링**을 통해 기반 모델의 잠재력을 최대한 활용하는 범용 패턴을 사용하는 것이다

### 4.3. 진화적 소프트웨어와 미래 비전
1. **The Weaving Loom 인프라**
   1. **The Weaving Loom**은 진화적 소프트웨어를 위한 인프라로 개발 중이다
   2. 이는 **레벨 9** 목표(자율 루프가 제품을 진화시키고 수익을 최적화)를 위한 것으로, **소프트웨어 공장**을 의미한다
2. **소프트웨어 개발의 종말과 새로운 엔지니어의 필요성**
   1. 소프트웨어 개발은 죽었으며, 이제 버거 뒤집는 사람 임금보다 싸게 AFK(자리 비움) 상태에서도 개발이 가능하다
   2. 미래를 위해 **근본 지식**을 가진 엔지니어가 필요하며, LLM이 새로운 형태의 프로그래밍 가능한 컴퓨터임을 이해해야 한다
   3. 코딩 에이전트를 직접 만들어보지 않았다면 만들어야 한다

### 4.4. 코딩 에이전트 구축과 최종 권고
1. **에이전트 구축의 용이성**
   1. 코딩 에이전트는 LLM 토큰을 넣어 루프를 도는 **300줄짜리 코드**로 만들 수 있다
2. **Loom과 시스템 검증**
   1. Loom은 **"모든 랄프 루프의 어머니"** 아래에 시스템 검증을 자동으로 수행하도록 설계되었다
   2. 발견된 결함은 정방향 랄프 루프로 수정되며, 모델 성능 향상 덕분에 이 비전이 실현 가능해졌다
3. **마지막 경고와 참여 독려**
   1. 젠가 탑을 쌓는 방식에 머무르는 엔지니어들은 주의해야 한다
   2. 독자들에게 **새로운 컴퓨터를 프로그래밍하는 법**을 배우고, **자동화된 소프트웨어 공장**을 만드는 우주 경쟁에 합류할 것을 촉구한다
