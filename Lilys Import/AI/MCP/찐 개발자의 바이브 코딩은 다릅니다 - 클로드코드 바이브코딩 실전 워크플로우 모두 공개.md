AI 코딩 도구의 한계를 극복하고 **진짜 개발자의 실력으로 코드를 완성하는 방법**을 알려드립니다. 복잡한 작업에서 AI 코딩이 무너지는 이유를 명확히 짚어주고, **'계획 검토 및 승인'이라는 단 하나의 원칙**으로 쓸데없는 삽질을 줄이고 주도권을 되찾는 실전 워크플로우를 공개합니다. AI를 단순 도구가 아닌 협업 파트너로 만들어 결과물의 완성도를 높이고 싶은 개발자라면 반드시 주목해야 할 내용입니다.

## 1. AI 코딩 도구의 한계를 극복하는 개발자 중심 워크플로우
AI 코딩 도구의 복잡한 작업에서의 한계를 극복하고, 개발자가 주도권을 가지고 결과물의 완성도를 높이는 실전 워크플로우를 제시한다.

### 1.1. 기존 AI 코딩 방식의 문제점과 핵심 원칙
대부분의 AI 코딩 방식은 작업이 복잡해지면 결과물이 무너지는 한계를 가지며, 이를 극복하기 위한 핵심 원칙은 '계획 검토 및 승인'이다.

1.  **기존 AI 코딩 방식의 한계**
    *   프롬프트 입력, 플랫 모드 사용, 에러 수정 반복 등의 방식은 작업이 복잡해지면 결과물이 무너진다.
    *   랄프루프, MCP, 스킬, 팀 에이전트 등 다양한 시도도 부차적이며 복잡한 작업에서는 한계를 보인다.
    *   아직 한계를 경험하지 못했다면, 그 수준의 복잡도를 만나지 못했을 뿐이다.

2.  **핵심 원칙: '계획 검토 및 승인'**
    *   작성된 계획을 개발자가 직접 검토하고 승인하기 전까지 AI에게 코드를 쓰게 하지 않는다.
    *   이는 '기획과 코딩의 분리'를 의미하며, 가장 중요한 단 하나의 원칙이다.
    *   이 원칙을 통해 쓸데없는 삽질이 사라지고, 아키텍처 결정의 주도권이 개발자에게 남으며, 토큰 사용량은 줄이고 결과물은 향상된다.

### 1.2. 실전 워크플로우 단계별 상세 설명
AI 코딩 워크플로우는 코드 리서치, 계획 수립, 구현, 피드백 반복의 단계를 거치며, 각 단계별로 개발자의 명확한 개입이 중요하다.

1.  **1단계: 코드 리서치 및 이해**
    *   모든 의미 있는 작업은 코드 베이스를 깊이 읽는 것부터 시작한다.
    *   AI에게 관련 부분을 철저히 이해시키고, 발견한 내용을 마크다운 파일(`research.md`)에 작성하게 한다.
    *   **주의:** 채팅창에서의 단순 요약으로 끝나지 않도록 해야 한다.
    *   **프롬프트 예시:**
        *   "이 폴더를 깊이 읽고 어떻게 동작하는지 깊이 이해하고 모든 세부 사항을 파악해라. 끝나면 리서치의 상세 보고서를 작성해라."
        *   "알림 시스템을 매우 상세에 연구하고 알림이 어떻게 작동하는지 모든 것을 담은 리서치 MD를 작성해라."
    *   **핵심 팁:** '깊이', '매우 상세히', '세부 사항'과 같은 단어를 사용하여 AI가 대충 훑어보는 것을 방지한다.
    *   AI의 구조는 강력한 인풋이 중요하며, 사람의 뇌와 크게 다르지 않다.
    *   **가장 비싼 실패:** 주변 시스템을 망가뜨리는 구현 (기존 레이어 무시, ORM 미고려 마이그레이션, 로직 중복 API 등)
    *   리서치 단계는 이러한 비싼 실패를 방지하는 역할을 한다.

2.  **2단계: 계획 수립 및 검토**
    *   리서치 후, 별도의 마크다운 파일(`plan.md`)에 상세 구현 계획을 작성하게 한다.
    *   **프롬프트 예시:**
        *   "세기능 ETF 리밸런싱을 구현하는 상세 플랜 MD를 작성해라. 코드 스니펫도 포함."
        *   "목록에서 오프셋 페이징 대신 인풋 기반 페이징을 지원해야 함. 이를 위한 상세 플랜 MD를 작성해 줘. 변경 사항을 제한하기 전에 소스 파일을 읽고 실제 코드베이스를 기반으로 계획을 작성해."
    *   **주의:** AI 코딩 도구의 내장 플랫 모드는 사용하지 않는 것이 좋다.
    *   **자체 MD 파일 사용 이유:** 에디터 편집 용이, 인라인 메모 가능, 프로젝트 산출물로 남음, 세션 날아감 방지 등 작업 연속성 유지.
    *   **계획 수립 및 검토 흐름:**
        *   AI가 플랜 MD 작성
        *   개발자가 에디터에서 검토, 주석, 메모 추가
        *   AI에게 다시 보내 계획 업데이트
        *   만족 시 투두 리스트 요청
    *   **개발자의 메모:** 잘못된 가정 수정, 접근 방식 거부, 제약 조건 추가, 도메인 지식 제공 등 다양한 역할을 한다.
        *   예시: "이건 풋이 아니라 패치어야 해" , "여기 캐싱 필요 없어" , "패런트가 제시도 처리하니까 이 제시도 로직은 중복이야. 제거하고 그냥 실패하게 둬"
    *   메모 추가 후 AI에게 다시 보내 업데이트를 요청하며, **"아직 구현하지 마"**라고 명시적으로 지시해야 한다.
    *   이 사이클은 1번에서 수번 반복되며, 개발자가 괜찮다고 할 때까지 충분하지 않은 것이다.

3.  **3단계: 구현 및 피드백**
    *   계획이 완전히 준비되면 구현 명령을 내린다.
    *   **표준 구현 프롬프트:** "전부 구현해라. 작업이나 단계를 완료하면 계획 문서에서 완료로 표시해라. 모든 작업과 단계가 완료될 때까지 멈추지 마라. 너운 타입을 쓰지 마라. 지속적으로 타입 체크를 실행해서 새로운 문제를 만들지 마라."
    *   구현 단계는 기계적이며 창의적이지 않아야 한다.
    *   개발자는 설계자/아키텍트에서 감독자로 역할이 바뀐다.
    *   **프롬프트 예시:** "리밸런스 이벤트 함수를 구현 안 했잖아." , "설정 페이지를 메인 앱에 만들었는데 어드민 앱에 있어야 해. 옮겨."
    *   프론트엔드 작업 시 브라우저 테스트를 통해 빠른 수정을 요청한다.
    *   디자인적 문제는 스크린샷 첨부가 효율적이다.
    *   **잘못된 방향 시 팁:** 깃을 통째로 되돌리고 범위를 재설정하는 것이 점진적 수정보다 낫다.
    *   개발자는 항상 운전대를 잡고 있어야 하며, 결정권을 AI에게 넘기지 않는다.

### 1.3. 개발자 주도권 유지를 위한 전략
개발자는 AI에게 실행 권한만 부여하고, 무엇을 만들지에 대한 결정권은 항상 자신이 가져야 한다.

1.  **적극적인 방향 조정**
    *   대부분의 방향 조정은 플랜 MD 문서 위에서 이루어진다.
    *   **예시:**
        *   "좋은 건 취하고 나머진 버리기: 첫 번째 방법은 어싱크로 깔끔하게 가자. 괜히 복잡하게 만들 필요 없어. 세 번째는 읽기 쉽게 함수로 분리해 줘. 네 번째랑 다섯 번째는 빼드리는 노력 대비 얻는 게 없어."
        *   "지금 안 할 건 과감하게 쳐내기: 다운로드 기능은 계획에서 빼. 지금 안 만들 거야."

2.  **건드리면 안 되는 선 긋기**
    *   특정 함수의 시그니처는 절대 바꾸지 않도록 명시한다.
    *   라이브러리가 호출자에게 맞추는 것이 아니라, 호출자가 라이브러리에 맞춰야 함을 강조한다.

3.  **기술 선택은 개발자가 하기**
    *   AI가 제안하는 모델 대신 특정 모델을 사용하도록 지시한다.
    *   직접 만들기보다 라이브러리에 이미 있는 메서드를 사용하도록 유도한다.

### 1.4. 단일 세션 워크플로우와 핵심 요약
리서치, 기획, 구현 단계를 별도 세션으로 나누지 않고 하나의 긴 세션으로 진행하며, 이는 AI의 컨텍스트 유지 능력과 계획 문서의 중요성 때문이다.

1.  **단일 세션 진행의 이점**
    *   리서치, 기획, 구현을 별도 세션으로 나누지 않고 하나의 긴 세션 안에서 쭉 이어간다.
    *   컨텍스트 윈도우 성능 저하 우려에도 불구하고, AI는 리서치와 계획 수립을 통해 이해를 쌓아오므로 성능 저하를 체감하지 못한다.
    *   컨텍스트 윈도우가 꽉 차면 AI의 오토 컴팩션이 맥락을 유지해 준다.
    *   계획 문서는 연구적인 파일로서 원본 그대로 살아남아 컨텍스트 유지에 기여한다.

2.  **핵심 요약 및 원리**
    *   마법 같은 프롬프트, 정교한 시스템 인스트럭션, 영리한 해킹 없이 규율 있는 파이프라인을 따른다.
    *   **파이프라인의 역할:**
        *   리서치: 무지한 변경 방지
        *   계획: 잘못된 변경 방지
        *   주석 달기 사이클: 개발자 판단 주입
        *   구현 명령: 결정 완료 후 방해 없이 실행
    *   **궁극적인 핵심:** AI에게 코드를 잘 쓰게 만드는 것이 아니라, 코드를 쓰기 전에 '무엇을 써야 하는지'를 확실하게 만드는 것이다.

### 1.5. 실용적인 인간 주도 루핑 방법론
'쉐어드 뮤터블 스테이트 패턴'을 활용하여 문서에 직접 메모를 추가하고 반복적으로 업데이트하는 방식으로 개발자 주도 루핑을 실현한다.

1.  **메모 추가 및 업데이트 방식**
    *   **메모 위치:** 플랜 MD 파일에 직접 인라인으로 추가한다.
    *   **업데이트 과정:**
        *   AI에게 메모 추가했으니 반영하고 업데이트하라고 보낸다.
        *   "아직 구현하지 마"라고 명시한다.
        *   만족할 때까지 이 과정을 반복한다 (1번에서 6번 반복).
    *   채팅창에서 설명하는 대신, 문서의 정확한 위치를 가리키며 수정 사항을 직접 적는 것이 중요하다.

2.  **방법론의 명칭**
    *   이는 '쉐어드 뮤터블 스테이트 패턴'이며, 에이전트 코딩 워크플로우에서 가장 실용적인 인간 주도 루핑 방법론이다.
