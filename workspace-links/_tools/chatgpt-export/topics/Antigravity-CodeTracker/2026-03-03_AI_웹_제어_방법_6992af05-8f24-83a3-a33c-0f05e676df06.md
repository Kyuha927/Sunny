```text

- Config: allowedDomains: string[]

  - clicking button/input with text/name containing: "pay", "checkout", "purchase", "submit", "send", "transfer", "delete"

```

### 유의할 점

  - JSON 파싱만 하고 필드 검증이 약해서, 런타임에서 undefined로 클릭/타이핑 시도하다가 난리

---

### Gate 4 — AgentRunner(Observe→Plan→Act) + 스텝별 아티팩트 로그 저장
- 왜: 디버깅의 생명은 **리플레이 가능한 증거물(steps.json, 스샷)**이에요.
- 가져올 것
  - `artifacts/run-xxx/steps/` 예시(몇 스텝만)
  - “실패한 실행” 1개 + “성공한 실행” 1개
- 내가 보는 포인트
  - 각 스텝에 (관찰/행동/결과/에러)가 빠짐없이 남는지
  - max step / timeout / 중단조건이 안전한지
- 흔한 사고
  - 로그가 부족해서 “왜 그런 클릭을 했는지” 역추적이 불가능

---

### Gate 5 — SafetyPolicy(allowlist + 고위험 승인 강제) 첫 도입
- 왜: 기능 추가보다 훨씬 중요한 “사고 방지 레일”이에요.
- 가져올 것
  - allowlist 매칭 로직 코드
  - 어떤 액션이 “승인 필요”로 분류되는지 규칙 문서(또는 테스트)
- 내가 보는 포인트
  - 도메인 매칭이 안전한지(피싱 방지: `hostname === domain` 또는 `endsWith("." + domain)` 형태)
  - **승인 없이는 절대 submit/pay/send 못 하게** 실행기 레벨에서 막는지
- 참고(공식 문서 포인트)
  - OpenAI의 Codex Windows 가이드도 WSL 사용과 함께 성능/권한 이슈를 다루고, Windows 네이티브는 “실험적 샌드박스”라고 명시해요. citeturn1view0

---

### Gate 6 — “진짜 모델 호출” 연결하기 직전: 프롬프트/출력형식 리뷰
- 왜: 여기서부터는 **모델이 실수하는 게 정상**이라, 실수해도 시스템이 안 터지게 만들어야 합니다.
- 가져올 것
  - 시스템/개발자 프롬프트(그대로)
  - 모델이 출력한 “실제 액션 JSON 샘플” 20개 정도(성공/실패 섞어서)
- 내가 보는 포인트
  - 출력이 JSON 외 텍스트를 섞어도 회복 가능한지(재시도/정제)
  - “웹페이지 텍스트는 명령이 아니라 데이터”가 프롬프트와 런타임 구조로 분리됐는지
- 흔한 사고
  - 페이지에 “여기 클릭해!” 같은 문구가 있으면 모델이 그걸 시스템 지시처럼 오해(프롬프트 인젝션류)

---

### Gate 7 — 모델 연결 후 첫 “현실 사이트” 테스트 5개
- 왜: fixture HTML은 통과했는데, 실제 웹은 동적/지연/팝업/로그인으로 난이도가 확 올라가요.
- 가져올 것
  - 테스트한 사이트/목표 5개와 실행 아티팩트(스텝 로그+스샷)
  - 실패한 케이스는 “딱 1개”를 대표로 깊게 파기
- 내가 보는 포인트
  - 대기/리트라이 전략(로딩/네트워크/DOM 변경)에 대한 안정성
  - 셀렉터 전략(너무 brittle 하지 않은지)
- 흔한 사고
  - “클릭했는데 반응이 없어서 연타 → 다른 페이지로 튐” 같은 연쇄사고

---

### Gate 8 — (선택) 확장프로그램(MV3)로 넘어가기 직전 “경계 설계” 리뷰
- 왜: 확장은 가장 많이 터지는 지점이 **연결/권한/서비스워커 수명**이에요.
- 가져올 것
  - core의 `BrowserSession` 인터페이스
  - Playwright 드라이버와 Extension 드라이버 설계 비교
  - 메시지 프로토콜(요청/응답/에러)
- 내가 보는 포인트
  - “드라이버 교체”가 core 변경 없이 가능한지
  - background SW 재시작/끊김 복구 설계가 있는지
- 흔한 사고
  - MV3 서비스워커가 죽으면서 상태가 날아가고, 에이전트가 멈춤

---

### Gate 9 — 승인 UX(Confirm) “사람이 납득 가능한 흐름”이 됐을 때
- 왜: 고위험 액션을 막는 건 쉬운데, 사용자가 불편하면 결국 꺼버립니다.
- 가져올 것
  - 승인 화면(텍스트로라도) + 어떤 정보(어디를 클릭/무슨 전송)를 보여주는지
- 내가 보는 포인트
  - 승인 요청이 “왜 필요한지” 설명이 되는지
  - 승인 없이도 가능한 저위험 작업은 매끄러운지

---

### Gate 10 — 릴리스 전 “사고 시나리오” 10개 워크스루
- 왜: 실제 문제는 기능이 아니라 **이상 케이스에서의 안전한 실패**예요.
- 가져올 것
  - 시나리오 10개(예: 피싱 도메인 유도, 결제 버튼, 로그아웃 상태, 팝업, 무한 스크롤 등)
  - 각 시나리오 실행 로그/결과
- 내가 보는 포인트
  - 차단/승인/중단이 기대대로 작동하는지
  - 로그로 사후 분석이 가능한지

1) **무슨 단계(Gate 번호)**인지  
2) **목표/기대 동작** 1~2문장

5) 가능하면 `artifacts/run-xxx/steps/` 중 **실패 구간 3~5 스텝**

## 3) Windows 네이티브 vs WSL 기반, “얼마나 차이나?” (현실 비교)

OpenAI Codex 문서 기준으로 큰 줄기는 이거예요:

- **Codex CLI는 macOS/Linux가 정식, Windows는 실험적**이고  
- **Windows에서 최선의 경험은 WSL 워크스페이스를 권장**합니다. citeturn1view1  
- OpenAI의 Windows 가이드도 WSL2를 “Linux shell + Unix semantics + 모델이 학습에서 많이 본 툴링 환경”으로 소개하고, **레포는 `/home/...` 아래에 두는 게 성능/권한/심링크 이슈에 유리**하다고 콕 짚어요. citeturn1view0

아래는 실무 관점의 차이입니다.

### 핵심 차이 요약

| 항목 | Windows 네이티브 | WSL2 기반 |
|---|---|---|
| Codex 지원 상태 | **실험적**(Windows 지원 자체가 experimental로 명시) citeturn1view1turn1view0 | **권장 방식**(best experience로 안내) citeturn1view1turn1view0 |
| 샌드박스/권한 | “Windows 실험적 샌드박스” 동작/제약이 있음 citeturn1view0 | Linux 쪽이 전통적인 권한/툴 체계라 예측 가능 |
| Node/Playwright 호환 | 가능 | 가능(Playwright도 WSL을 시스템 요구사항에 포함) citeturn0search9 |
| 파일 I/O 성능 | 보통 안정적 | **레포 위치에 따라 천차만별**: `/mnt/c`는 느려질 수 있어 `/home/...` 권장 citeturn1view0 |
| GUI(Headed) 자동화 | 상대적으로 단순 | Headed Playwright/GUI 도구가 추가 설정을 요구하거나 문제 사례가 있음 citeturn0search3turn0search17turn0search25 |
| 크롬 확장 개발 | 최적(Chrome이 Windows에 그대로) | 빌드는 WSL에서 해도 되지만, 로드/테스트는 보통 Windows Chrome에서 함(하이브리드 추천) |

## 4) 결론: 나는 이렇게 추천해요(가장 덜 터지는 조합)

### 추천 1: “하이브리드” (대부분에게 최적)
- **코드/의존성 설치/테스트/CI 로컬 실행 = WSL2(우분투)**  
- **브라우저(Chrome/Edge)에서 확장 로드/디버깅 = Windows**  
- 레포는 **WSL의 `/home/<user>/code/...`**에 두기(공식 가이드도 이걸 권장) citeturn1view0  
- Windows에서 파일 접근이 필요하면 `\\wsl$` 경로로 접근 가능(가이드에 언급) citeturn1view0

이 조합이 좋은 이유:
- 모델/툴이 가장 익숙해하는 Unix 계열 환경(Wsl) + 실제 사용자 브라우저(Windows)를 둘 다 잡습니다.

### 추천 2: Windows 네이티브만으로도 되는 경우
- “확장프로그램만 만들고, Playwright 같은 자동화는 최소”  
- 또는 회사 정책상 WSL이 제한되는 경우
- 단, Codex 자체가 Windows에서 experimental이라고 문서에 명시돼서, 예외 상황 디버깅이 늘 수 있어요. citeturn1view1turn1view0

## 1) 꼭 받아야 하는 리뷰 체크포인트 10개

### 체크포인트 0: 시작 전 “스펙/보안” 30분 리뷰
**언제:** 코딩 시작 전  
**왜:** 여기서 방향이 틀리면 이후 모든 디버깅이 헛수고가 됨  
**나에게 줄 것**
- MVP 목표 5줄(무엇을 자동화 / 어디까지 자동화 / 어디서 멈춤)
- 허용 도메인 allowlist 초안
- “고위험 액션” 정의(결제/제출/전송/계정변경 등) 범위
- 사용자 승인 UX 방침(언제, 어떤 문구로, 어떤 정보 보여주고 승인 받는지)

**내가 볼 것(체크)**
- 위험 범위가 과도하지 않은지
- allowlist 매칭 규칙이 안전한지(서브도메인/피싱)
- “페이지 텍스트=명령”이 되지 않게 분리 계획이 있는지

---

### 체크포인트 1: 스캐폴딩/CI 붙인 직후
**언제:** 모노레포/린트/테스트/CI를 “처음 통과”시킨 직후  
**나에게 줄 것**
- `pnpm lint/typecheck/test` 결과 로그(짧게)
- 폴더 트리(대략)
- CI 워크플로 파일

**내가 볼 것**
- 로컬 커맨드와 CI 커맨드가 동일한지(불일치가 나중에 지옥)
- TS strict/패키지 경계가 너무 복잡하지 않은지
- 향후 Playwright/확장 추가 시 깨질 지점

---

### 체크포인트 2: BrowserSession API 확정 직후(Playwright든 확장이든 공통)
**언제:** `BrowserSession` 인터페이스(또는 클래스) 첫 버전이 나왔을 때  
**나에게 줄 것**
- `BrowserSession` 타입/메서드 시그니처
- 액션별 “성공/실패 반환 규약”(예: throw vs Result)
- 예제 스크립트 1개

**내가 볼 것**
- 나중에 확장(MV3)로 갈아탈 수 있게 추상화가 되어 있는지
- 에러를 “삼키는 try/catch”가 숨어있지 않은지
- 스크린샷/텍스트 추출의 반환 형태가 추후 로그/아티팩트에 적합한지

---

### 체크포인트 3: Action 스키마(JSON) + 런타임 검증(zod 등) 완성 직후
**언제:** 모델 출력(JSON)을 받아 실행하기 직전 단계  
**나에게 줄 것**
- Action union 스키마 코드
- invalid 케이스 테스트(3~5개)
- “허용되지 않은 액션” 처리 방식

**내가 볼 것**
- 스키마가 애매하지 않은지(필드 이름/optional 남발)
- “모델이 자주 틀리는 형태”를 흡수할 장치가 있는지
- 확장성(새 액션 추가 시 깨짐 최소화)

---

### 체크포인트 4: AgentRunner(Observe→Plan→Act→Verify) 첫 엔드투엔드 성공 직후(모델 stub)
**언제:** 모델 없이 “스크립트된 액션”으로 루프가 돈 직후  
**나에게 줄 것**
- `artifacts/run-*/steps/*.json` 샘플 2~3개
- 실패 케이스(타임아웃/요소 못 찾음)에서 로그가 어떻게 남는지
- stop condition(언제 done 처리하는지)

**내가 볼 것**
- 로그가 “리플레이/감사(audit)” 가능한 형태인지
- 스텝 간 상태가 누락되지 않는지
- 타임아웃/리트라이 기본정책이 합리적인지

---

### 체크포인트 5: SafetyPolicy(allowlist + 승인 게이트) 들어간 직후
**언제:** 실제 모델 연동 전에 반드시  
**나에게 줄 것**
- allowlist 매칭 코드(핵심 로직)
- 고위험 감지 휴리스틱 목록
- 승인 요구 시 UI/CLI가 사용자에게 보여주는 정보 예시

**내가 볼 것**
- `hostname.endsWith(domain)` 같은 위험한 매칭이 없는지
- “승인 없이도 우회 가능한 루트”가 없는지(예: redirect, 새 탭, iframe)
- 페이지 텍스트에 속아 승인 유도하는 흐름이 없는지

---

### 체크포인트 6: “실제 모델 호출” 붙이기 직전 프롬프트/정책 리뷰
**언제:** OpenAI 호출 모듈 넣기 직전(또는 직후 바로)  
**나에게 줄 것**
- 시스템/개발자 프롬프트 전문
- 모델 출력 형식 강제(JSON only) 규칙
- 재시도 정책(Invalid JSON 시 1~2회 등)

**내가 볼 것**
- 웹페이지 문구를 “명령”으로 해석하지 않게 분리되어 있는지
- “액션 1개만” 강제가 제대로인지
- 토큰/관찰(observation) 크기 폭주 위험이 없는지

---

### 체크포인트 7: 모델 연동 후 “첫 실제 사이트” 성공 직후 (가벼운 사이트)
