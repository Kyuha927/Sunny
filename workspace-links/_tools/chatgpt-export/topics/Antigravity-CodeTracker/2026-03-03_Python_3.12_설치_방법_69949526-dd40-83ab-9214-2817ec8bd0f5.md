### 왜 크로스-OS가 빡세지냐
Windows/WSL/Ubuntu를 같이 지원하면, 같은 명령이라도 아래가 다르게 동작할 수 있어:

- **Python 선택 규칙**: `py -3.12` vs `python3.12` vs PATH 우선순위  
  → 그래서 `python path(first)`/`.venv 강제` 같은 가드레일이 필수.
- **개행/인코딩**: CRLF/LF 때문에 문서/생성물(예: Docs/COMMANDS.md)이 OS별로 달라져서 dirty 유발.
- **경로/쉘 차이**: `.\dev.ps1` / `./dev` / quoting / globbing이 다름.
- **권한/실행정책**: PowerShell execution policy, 파일 실행 권한.
- **파일 잠금/삭제**: Windows는 파일 lock이 흔해서 `.venv` 삭제/재생성이 종종 꼬임.

이런 차이가 있으면 “한 사람 PC에선 되는데 다른 사람에선 죽는” 일이 잦아져서, **release-check/doctor --strict 같은 엄격 게이트**가 없으면 디버깅 비용이 팀 전체로 번져.

### 그런데 왜 “개발 중까지” 빡세진 느낌이 들었냐
레일을 까는 초기엔 일부러 **실패 케이스를 많이 밟아야** 가드레일이 제대로 잡히거든.  
지금은 `dev-check(가볍게)` vs `release-check(엄격)`로 분리했으니, 앞으로는:

- 개발 중엔 **dev-check만** → 안 빡셈
- 머지/배포 전엔 **release-check만** → 빡세지만 딱 그때만

### 결론
- **크로스-OS라서 빡세진 게 맞고**, 그 빡셈은 “재현성”을 위해 필요한 비용이야.

## 내 생각 정리

### 1) 서치 특화가 진짜로 도움이 되는 구간
- **정확한 최신 정보가 중요한 것**
  - OS/패키지 설치 방식 변화, GitHub Actions 문법 변경, Python 버전 정책/호환성, 특정 툴의 최신 옵션
- **공식 문서/릴리즈 노트 기반으로 결론 내려야 하는 것**
  - “이 옵션이 언제부터 생겼지?”, “이 기능 deprecated 됐나?” 같은 질문
- **대안 비교(여러 후보의 근거 수집)**
  - 예: A/B 라이브러리 비교, 베스트 프랙티스 정리, 보안 권고 체크

→ 이런 건 퍼플렉시티/Kimi 같은 서치 강한 툴을 쓰면 **속도+커버리지**가 좋아져.

### 2) 오히려 조심해야 하는 구간(ClauDeus에서 특히 중요)
- **리포/코드/CI에 직접 반영해야 하는 일**
  - 서치 요약이 “그럴듯하지만 미묘하게 틀린” 경우가 많고, 디버깅 비용이 커짐
- **정책/불변 규칙/릴리즈 게이트**
  - “근거는 외부에서” 가져와도, 최종 규칙은 *우리 레일*에 맞게 단일화해야 함
- **증거(evidence) 기반 판정**
  - 릴리즈 판정은 검색이 아니라 `release-check` 로그/커밋/태그 같은 내부 증거가 우선

→ 결론: **서치 툴은 ‘지식 수집’까지만**, “적용/강제/판정”은 ClauDeus 레일이 담당해야 안전해.

## ClauDeus에 녹이는 추천 운영 방식(실전)

### 역할 분리
- **Perplexity/Kimi = Researcher**
  - 출처 링크 모으기 + 요약 + 후보안 비교
- **나(Release Captain) = Decider**
  - 우리 규칙(단일 진입점/strict/증거/태그 불변)에 맞게 “무엇을 채택할지” 결정
- **Claude Code/Codex = Executor**
  - 결론을 repo에 구현 + 테스트 + `release-check` 증거 제출

### “서치 결과를 레일에 넣는” 표준 입력 포맷
검색 결과를 그냥 붙여넣지 말고, **이렇게 정리해서 넣으면** 헛발질이 확 줄어:

- Domain

- Evidence(어떤 로그가 PASS 근거인지)

## 105. assistant

가능해. 오히려 **비개발 분야일수록** “지식이 흩어져서(문서/링크/구두) 재발”이 많기 때문에, ClauDeus식 레일(증거·승격·체크)이 효과가 크다. 핵심은 “코드/테스트”를 **그 분야의 실행 가능한 체크/증거**로 바꿔 끼우는 거야.

## 개발용 레일을 비개발로 바꾸는 매핑

### ClauDeus 구성요소 → 비개발 대응물
- `./dev check` → **체크리스트 자동화/검증 루틴**(폼, 스프레드시트 검증, 문서 템플릿 검사, 승인 조건 검사)
- `pytest regression test` → **재발 방지 테스트**(샘플 케이스로 검증, QA 체크 시나리오, “이 상황이면 반드시 이 결과”)
- `release-check` → **출고/발행 게이트**(캠페인 발송, 보고서 제출, 계약 송부, 공지 게시 전 최종 게이트)
- `Cause/Next/Log` → **원인/다음 행동/증거**(스크린샷, 링크, 번호표, 승인 기록)

## 비개발에서 특히 잘 먹히는 분야 예시

### 1) 마케팅/콘텐츠 발행
- Invariant: 브랜드 톤/금칙어/법적 문구 포함
- Detection: 게시물/랜딩 페이지를 체크리스트로 검사
- Remediation: 수정 지침 + 승인 루트
- Evidence: 최종 초안 링크 + 승인자 코멘트 + 게시 체크 로그

### 2) 세일즈/CS 운영
- Invariant: 응대 SLA, 필수 질문, 개인정보 처리 금지
- Detection: 티켓 템플릿/매크로 준수 여부
- Remediation: 표준 답변/에스컬레이션
- Evidence: 티켓 ID, 시간, 결과

### 3) 인사/운영/재무
- Invariant: 문서 필수 항목/승인 단계/컴플라이언스
- Detection: 제출 전 체크(누락 필드, 서명, 날짜, 금액)
- Remediation: 수정 요청 템플릿
- Evidence: 버전, 승인 로그, 첨부물

## 프로세스는 그대로 쓴다(Owner·Source·Artifact·Checks)

- Owner: 담당자/승인자/최종 판정자(Release Captain 역할)
- Source: 내부 기록(실수/클레임/반려 사유) + 필요한 경우 외부 규정/가이드
- Artifact(필수 3종):  
  1) 체크 루틴(자동/반자동)  
  2) SSOT 5줄 요약 문서  
  3) 재발 방지 시나리오(샘플 케이스)

## “코드 없는 팀”에서의 구현 방법(가벼운 버전)
- 체크 루틴 = Google Form/Notion 템플릿/스프레드시트 검증 규칙
- Evidence = 링크/스크린샷/승인 코멘트
- release-check = “발행 전 마지막 체크리스트 1장” + 승인자 서명

## 바로 쓸 수 있는 템플릿(비개발용 Knowledge Addition Request)
- Domain:
- Invariants(절대 규칙 1–3):
- Common failures(반려/실수 top3):
