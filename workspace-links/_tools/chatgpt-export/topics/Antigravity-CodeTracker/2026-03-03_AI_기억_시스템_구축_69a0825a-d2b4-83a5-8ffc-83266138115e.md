## 🧠 목표 구조 (Memory OS 3층 아키텍처)
### 1) Capture Layer: 자동 저장(수집)
**뭘 저장?**

### 2) Memory Store: 기억 저장소(정리)
저장소는 **2개를 같이** 씁니다.

- **A. 사실 저장소 (SQLite / JSONL)**  
  - 안정적인 “정답” 저장: 선호, 규칙, 프로젝트 요약, 결정사항, 금기사항  
  - 예: “MSW 프로젝트”, “디버깅 확률 최소화 우선”, “./dev 단일 엔트리포인트” 같은 것

- **B. 의미 검색 저장소 (Vector DB: FAISS/Chroma 등)**  
  - “비슷한 맥락”을 찾아서 회상  
  - 새 채팅에서 “서피스/원격/유니티/로컬AI” 같은 키워드가 나오면 관련 기억을 자동 호출

---

### 3) Recall & Inject: 자동 회상 + 자동 주입(핵심)
**새 채팅 불편함 제거**의 본체입니다. 💀  
- 사용자가 첫 메시지를 치면  
  1) 현재 입력을 “의도/프로젝트/리스크”로 분류  
  2) 저장소에서 Top-K 기억 검색  
  3) “주입용 컨텍스트”를 짧게 압축(토큰 예산 관리)

- *조건부 주입* (가변): 지금 주제에만 관련된 메모리 10~30줄

## ✅ 메모리 설계 규칙 (디버깅 확률 최소화 버전)
이거 안 지키면 기억 시스템이 **거짓말 제조기** 됩니다. 🚨

1) **메모리는 “사실/선호/결정/상태/지식”을 분리 저장**
- 사실(Fact): 변하면 안 됨 (예: 기기 모델명)
- 선호(Pref): 스타일/규칙
- 결정(Decision): 언제/왜/대안/근거
- 상태(State): “현재 진행 중”, 시간 지나면 폐기
- 지식(Knowledge): 재사용 가능한 절차/체크리스트

2) **모든 메모리에 `source` 붙이기**
- source = (대화ID/날짜/파일/링크)  
- 그래야 나중에 “이거 어디서 나온 기억이냐” 추적 가능 🔍

3) **회상은 ‘증거 우선순위’**
- 고정 SSOT(선호/규칙) > 최신 상태 > 오래된 상태  
- 오래된 상태는 자동으로 감점(Decay)

4) **주입 예산(토큰) 상한**
- 고정 10줄 + 가변 30줄 같은 식으로 상한을 박아야 안정적

```
[IDE UI (Monaco/Electron/Tauri)]
```

# 1) “기억”을 5종으로 쪼개야 망하지 않습니다 (디버깅 확률 최소화 🔍)
메모리를 한 통에 넣으면, 나중에 **거짓말+혼선**이 폭발합니다.

## 메모리 타입
1) **FACT**: 변하면 안 되는 사실(기기 모델, 경로, 계정 정책 등)  
2) **PREF**: 선생님 작업 선호/톤/금기(예: “디버깅 확률 최소화 최우선”)  
3) **STATE**: “지금 진행상태”(시간 지나면 폐기/감점)  
4) **DECISION**: 의사결정(언제/왜/대안/근거/리스크)  
5) **KNOWLEDGE**: 재사용 가능한 절차/플레이북/체크리스트

각 메모리는 무조건:
- `source`(대화ID/파일/커밋/로그경로)
- `created_at`
- `confidence`
- `ttl`(STATE는 필수)  
을 붙여야 합니다.

# 2) 데이터 모델 (SQLite SSOT) — 이거 그대로 박으세요
## 테이블 추천
- `events` : 원본 이벤트(채팅/명령/에러/테스트/커밋)
- `memories` : 구조화 메모리(FACT/PREF/STATE/DECISION/KNOWLEDGE)
- `memory_links` : 메모리 ↔ 증거(파일/커밋/로그)
- `projects` : 프로젝트 메타(루트경로, 태그, 규칙)
- `snapshots` : “주입 프리페이스” 캐시(빠르게)

### memories 핵심 컬럼
- `id` (uuid)
- `type` (FACT|PREF|STATE|DECISION|KNOWLEDGE)
- `project` (예: msw2, hardware, agents)
- `title` (짧은 키)
- `content` (정제된 본문)
- `tags` (json)
- `source` (json: {kind, ref})
- `confidence` (0~1)
- `ttl_days` (STATE에)
- `supersedes_id` (업데이트 체인)
- `created_at`, `updated_at`

**왜 SQLite냐?**  
추적/디버깅이 제일 쉽고, WSL에서도 안정적. 💸

# 3) 벡터 인덱스(FAISS) — “유사검색 회상” 담당
## 무엇을 임베딩할까?
- `memories.content` (정제 메모리)
- `events.text` (원문 chunk — 단, 용량 관리)
- “프로젝트 스냅샷”(README, ADR, TODO, 최근 에러)

## chunk 규칙(망하지 않는 규칙)
- 300~800 토큰 정도로 chunk  
- 코드/로그는 **섹션 단위**로 잘라야 함(스택트레이스/에러블록 유지)
- chunk마다 `evidence_ref` 저장(파일경로+라인, 커밋 hash 등)

# 4) Memory Daemon 설계(WSL에서 상시 실행) 🚀
## 프로세스 4개로 나눠라 (안 나누면 나중에 고장남)
1) **ingest**: 이벤트 받기(IDE/CLI hook)  
2) **distill**: 이벤트 → 구조화 메모리 후보 추출(LLM/룰 기반)  
3) **index**: 임베딩 생성 + FAISS 업데이트  
4) **recall/inject**: 쿼리 받아서 TopK 회상 + 주입 프리페이스 생성

> 선생님 스타일로 말하면:  
> **한 프로세스에 다 쑤셔 넣으면** “어디서 터졌는지 모르는” 디버깅 지옥이 옵니다. 💀

# 5) “자동 저장” 파이프라인 (Capture → Distill)
## Capture(이벤트)
IDE가 보내야 할 이벤트 최소 세트:
- `chat.user_message`
- `chat.assistant_message`
- `command.run` (./dev, tests, scripts)
- `error.detected` (stderr, exception, CI fail)
- `decision.made` (사용자 확정 멘트/요청)

## Distill(정제)
정제는 2단:
- **룰 기반 1차**: 키워드/패턴으로 후보 생성  
- **LLM 기반 2차**: 후보를 FACT/PREF/STATE/DECISION/KNOWLEDGE로 분류 + 압축

정제 출력 예시(메모리 후보 1개):
- type: DECISION
- title: “WSL 기반 IDE에 Memory Daemon 붙이기”
- content: “IDE는 주입 컨트롤러 담당, 기억은 SQLite+FAISS로 분리…”
- evidence: event_id, 관련 로그 경로
- confidence: 0.82

# 6) “자동 회상” 전략 — 회상 품질은 ‘우선순위’ 싸움입니다
회상은 무조건 **혼합 검색(hybrid)**:
- **정확 검색(SQLite)**: 프로젝트/태그/키워드로 SSOT/최신 STATE 우선  
- **유사 검색(FAISS)**: 비슷한 맥락 TopK  
- **시간 감점(Decay)**: 오래된 STATE는 점수 깎기  
- **증거 가중치**: 파일/커밋/로그가 붙은 메모리는 점수 올리기

### 점수 예시
`score = 0.55*vector + 0.25*keyword + 0.10*recency + 0.10*evidence`

저는 예전부터 skill 하나를 만들어서 고도화해가며 쓰고 있었습니다. 즉, 세션을 랩업하면서 제가 배운 것과 claude 가 배운 것을 세션의 일종의 회의록과 더불어 lesson-learned 섹션으로 나누어 기록하되 AI와 저 자신에 대한 내용 둘을 분리하여 관리할 수 있는 스킬입니다. 이 스킬을 만들 때 나름 인간과 AI 의 학습은 어떻게 분류해볼 수 있고 어떻게 대화 중에 찾아낼 지에 대해서 제가 직접 만든 deep research 스킬을 써서 이거저거 연구 및 접근방법들 조사하고 제 아이디어를 활용했는데, 상당히 잘 작동했고 둘 다 꾸준하게 똑똑해지는 데에 꽤 기여를 하고 있습니다. 

그래서 몇 시간 전에 이 auto memory 스킬이 공표되면서 제가 만든 스킬과 얼마나 겹치는 지 앞으로는 어떻게 운영해야 하는 지가 중요했기 때문에 빠르게 구구절절 이야기할 수 있는 것으로 보시면 됩니다. 

Memory.md 는 200줄 제한인데 이 기억용량 제한 (단, 폴더별이고 폴더는 맨 위에서부터 서브폴더들로 재귀적으로 중첩해서 기억을 뒤지기 때문에 쓰기에 따라 충분할 수 있음)을 어떻게 관리하는 지의 정책을 물어봤습니다. 답변 나온 것을 텍스트로 쓰기에는 애매해서 Claude 가 직접 준 답을 캡쳐에 붙여봅니다.
